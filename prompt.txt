## 5. Upload lifecycle

Only after explaining the reusable architecture should the artifact follow the upload flow.

Introduce the three phases:

1. Stage each file.
2. Finalize successfully staged document IDs.
3. Process asynchronously and deliver the result.

Show this formula prominently:

    N selected files
    → N staging requests
    → 1 finalize request
    → up to N queue jobs
    → 1 completion notification
    → 0 polling requests

Do not overload the diagram with controller or action class names.

Then explain the lifecycle once in five compact steps.

### Step 1: Stage

- The browser sends one request per selected file.
- Requests run in parallel.
- Each file has independent progress and cancellation.
- The server authorizes the target owner.
- The server validates the file.
- The file is written to staging storage.
- A pending Document row is created.
- The returned resource is inserted into the current UI.

### Step 2: Finalize

- The browser waits for all staging attempts to settle.
- It sends one request containing only successful document IDs.
- Submitted IDs are untrusted.
- The server re-scopes them by organization, uploader, owner, and pending status.
- One queue job is dispatched per accepted document.

### Step 3: Process

- Each job handles one document.
- It moves or copies the staged file to a deterministic permanent path.
- It updates the document to completed or failed.
- Documents retry independently.

### Step 4: Notify

- The batch callback re-reads final statuses from the database.
- One logical completion event is created.
- It is persisted through the database notification channel.
- The same payload is broadcast to the uploader.

### Step 5: Reconcile

- An active matching page patches its current document rows.
- A page entered later reconciles pending rows through a scoped reload.
- There is no polling loop.
- No full-page reload is required.

Do not repeat this lifecycle in later sections.

## 6. Lifetime and navigation model

Make the separation of lifetimes a central architectural idea.

Explain three distinct lifetimes.

### Page component lifetime

A Vue page may unmount because the user navigates elsewhere through Inertia.

The upload lifecycle must not be owned exclusively by that page instance.

### Browser upload-session lifetime

Active upload state lives in module scope through the composable.

It survives:

- Inertia navigation;
- leaving the Client Documents page;
- returning while uploads are still active.

It does not survive:

- browser refresh;
- browser tab close.

This is an intentional scope boundary.

### Server processing lifetime

Once the finalize request dispatches the batch, processing is independent of the frontend.

It continues regardless of:

- which page is open;
- whether the initiating component still exists;
- whether the user navigated elsewhere.

## 10. Architecture decisions and trade-offs

Use one compact table.

| Decision | Why | Trade-off |
|---|---|---|
| Polymorphic Documentable | Reuse the same document infrastructure across owners | Owner-specific policy and routing remain at integration boundaries |
| Shared backend pipeline | Avoid duplicate storage and queue logic | More indirection than page-specific code |
| Reusable frontend components | Keep document UX consistent across pages | Components depend on stable shared contracts |
| Module-scoped composable state | Let upload progress survive Inertia navigation | Does not survive refresh or tab close |
| One request per file | Independent progress, cancellation, and failure | More HTTP requests |
| Staging before permanent storage | Keep slow permanent storage off the request path | Requires cleanup and transition logic |
| Durable pending document row | Give each upload a stable identity and status | Requires stale-pending pruning |
| One job per document | Isolate retries and failures | Adds queue overhead |
| Uploader self-notification | Decouple completion from the initiating page | Requires subject filtering and reconciliation |
| Push-first, reconcile-on-entry | Deliver immediate updates without polling | Requires a fallback reconciliation request |
| Deterministic permanent paths | Support safe retries and avoid collisions | Existing-file checks may need stronger integrity guarantees |
| No polling | Avoid repeated status requests | Live delivery and reconciliation must remain reliable |

Keep entries concise.
